# 招聘情报 Agent 详细开发计划

> English mirror: [`en-US/DEVELOPMENT_PLAN.md`](en-US/DEVELOPMENT_PLAN.md)
> 项目代号：JOBAGENT V1.0  
> 文档状态：可执行基线（Baseline）  
> 适用对象：单人开发者（同时承担产品、开发、测试与运维）  
> 计划周期：10 周；第 8 周形成可日常使用的 MVP，第 10 周完成 Agent 增强版

## 1. 项目定义

### 1.1 一句话定位

一个面向个人的招聘情报系统：自动采集企业校招、公务员和事业单位招聘信息，解析公告及附件，按个人偏好筛选排序，并生成每日可行动的招聘情报。

### 1.2 核心价值链

```text
来源监控 → 增量采集 → 原文留存 → 附件解析 → 岗位结构化
        → 质量校验 → 规则匹配 → 日报生成 → 消息推送 → 自然语言查询
```

本项目的核心资产是稳定、可追溯的招聘数据，而不是聊天界面。Agent 是数据系统之上的查询和操作入口。

### 1.3 目标用户与运行边界

- 初期只服务一个用户，不建设注册、租户、权限和付费体系。
- 优先覆盖公开、无需登录且允许合理访问的信息源。
- 系统提供“发现、理解、排序、提醒”，不提供自动投递。
- 每日运行一次即可；不追求秒级更新和高并发。

## 2. 版本范围

### 2.1 MVP（第 8 周）

- 接入 5 个稳定来源，至少覆盖企业校招、公务员/事业单位两类信息。
- 支持静态 HTML 列表页和详情页的增量采集。
- 保存公告原文、来源地址、抓取时间和内容指纹。
- 下载并解析 PDF、XLSX/XLS 附件；扫描 PDF 可标记为待人工处理。
- 结构化公告和岗位，保留字段来源及抽取置信度。
- 支持个人偏好配置和可解释的规则评分。
- 自动生成 Markdown/HTML 日报并通过一个微信通道推送。
- 提供运行日志、失败重试和最小健康检查。

### 2.2 Agent 增强版（第 10 周）

- 支持自然语言查询岗位、查看详情和解释推荐分数。
- 支持受控触发采集和重新生成日报。
- Agent 只调用明确工具，不直接写数据库或执行任意代码。

### 2.3 来源扩展轨道（不阻塞 MVP 发布）

- 现有网站库的 11 个官方候选站全部进入实施路线：MVP 保持 5 个稳定来源目标，其余来源在公共流水线稳定后逐站接入。
- 新增外企招聘专区，首批候选为 Apple、Microsoft、Siemens、SAP、P&G 官方招聘站；按 `foreign_enterprise` 分类，覆盖中国及江浙沪职位。
- BOSS 直聘等商业招聘平台仅作人工交叉参考。平台条款不允许自动抓取时不开发 Adapter；未来只有取得官方 API、合作数据或书面授权后才评估机器集成。
- “全部纳入路线”不是强制绕过限制：需要登录、验证码、反爬规避或条款不允许的来源保持 `planned`/`blocked`，并寻找同一官方主体的公开公告入口。

### 2.4 双语文档治理轨道（不阻塞产品主线）

- JAI-046 已确立英文与简体中文使用独立文件、同提交同步，以及仓库级 Git 作者身份规则。
- JAI-047 为本次实质修改的开发计划和 Issue Backlog 补齐英文镜像，并把混合语言 WORKLOG 原样归档后拆成独立的中英文活动日志。
- JAI-048 负责其余存量单语文档的迁移盘点和分批补齐；任何功能 Issue 若先实质修改相关文档，必须在同一提交补齐缺失版本。
- 历史归档不回译、不删改；代码标识符、环境变量、错误码、URL 和命令保持原样。

### 2.5 暂不纳入 V1

- 多用户、登录、权限、订阅与商业化。
- 招聘平台账号登录、验证码绕过和自动投递。
- Elasticsearch、独立向量数据库、Kubernetes、微服务。
- 自动发现任意网站、通用“万能爬虫”。
- 多 Agent 协作、复杂长期记忆。
- 完整招聘网站式前端；只做必要配置和运行状态页面。

## 3. 成功指标与验收口径

| 指标 | MVP 目标 | 统计口径 |
|---|---:|---|
| 来源可用率 | ≥ 90% | 近 7 天计划任务中成功执行的来源比例 |
| 重复公告率 | ≤ 2% | 同一来源中经 URL/内容指纹判定的重复记录 |
| 核心字段完整率 | ≥ 85% | 单位、标题、地区、报名截止、来源链接五项的完整比例 |
| 附件解析成功率 | ≥ 80% | 可读取的文本 PDF 和表格附件，不含损坏/加密文件 |
| 日报准时率 | ≥ 95% | 近 20 次计划运行在目标时间窗口内完成的比例 |
| 可追溯率 | 100% | 每条推荐均可回到原公告或附件 |
| 单日人工维护 | ≤ 10 分钟 | 正常运行时检查和处理异常所需时间 |

任何 LLM 抽取结果都不能覆盖原始数据；关键日期必须能够定位到原文证据。推荐分数是排序信号，不对录用概率作承诺。

## 4. 技术方案

### 4.1 技术栈

| 模块 | V1 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.11+ | 复用现有 Python 环境，单语言降低个人维护成本 |
| Web/API | FastAPI + Pydantic v2 | 提供健康检查、配置和查询 API |
| ORM/迁移 | SQLAlchemy 2 + Alembic | 明确模型与迁移历史 |
| 数据库 | PostgreSQL 16 | 结构化数据、JSONB 和后续 pgvector 均可承载 |
| HTTP/HTML | httpx + selectolax/BeautifulSoup | 静态站点优先，Playwright 按需加入 |
| 任务调度 | APScheduler | V1 单实例足够；暂不上 Celery/Redis |
| PDF | PyMuPDF | 文本提取、页级证据定位 |
| 表格 | pandas + openpyxl | XLSX 清洗和表头识别 |
| LLM | OpenAI 兼容接口 + 可替换 provider | 仅用于不稳定结构的抽取和解释 |
| 测试 | pytest + pytest-asyncio | 单元、集成和固定样本回归 |
| 运行 | Docker Compose | API、worker、PostgreSQL 本地一键启动 |
| 观测 | 标准结构化日志 + 数据库运行记录 | 避免过早引入大型监控栈 |

### 4.3 运行架构

```text
APScheduler/手动触发
        │
        ▼
 Pipeline Orchestrator ──→ Crawl Run / Step Logs
        │
        ├─ Source Adapter → Raw Document → Attachment Store
        │
        ├─ Parser → Extractor → Validator
        │
        ├─ Matcher → Recommendation
        │
        └─ Reporter → Notifier
                              
FastAPI ──→ PostgreSQL ←── Agent Tools（第 9–10 周）
```

采集、解析、评分和推送保持普通 Python 服务；Agent 只能调用这些已有服务，避免把稳定业务逻辑写进 Prompt。

## 5. 核心数据模型

| 实体 | 用途 | 关键字段 |
|---|---|---|
| `sources` | 来源配置 | name、base_url、category、adapter、enabled、crawl_interval |
| `crawl_runs` | 一次来源运行 | source_id、status、started_at、finished_at、stats、error |
| `raw_documents` | 不可变公告原文 | source_id、canonical_url、title、raw_html/text、published_at、content_hash |
| `attachments` | 附件及解析状态 | document_id、url、file_name、mime_type、sha256、local_path、parse_status |
| `job_posts` | 公告级结构化结果 | document_id、organization、category、region、apply_url、start_at、deadline |
| `job_positions` | 公告下岗位明细 | post_id、name、department、location、education、major、headcount、requirements |
| `field_evidence` | 字段证据 | entity_type、entity_id、field_name、source_type、quote/page/cell、confidence |
| `user_preferences` | 单用户画像 | regions、education、majors、job_keywords、organization_types、exclusions |
| `match_results` | 可复算的评分结果 | position_id、score、score_version、components、matched_rules、generated_at |
| `reports` | 日报快照 | report_date、format、content、item_count、status |
| `notifications` | 推送记录 | report_id、channel、status、attempts、sent_at、error |

关键约束：

- `raw_documents(source_id, canonical_url)` 唯一；内容指纹作为页面换址或更新的辅助判断。
- 原文和附件解析结果可追加版本，不原地覆盖来源证据。
- `job_positions` 允许为空：公告级信息仍应保存，并进入“需要确认”分组。
- 所有时间入库使用 UTC，展示和调度使用 `Asia/Shanghai`。
- 删除来源不级联删除历史公告，默认仅停用。

## 6. 核心流程设计

### 6.1 增量采集

1. 调度器为启用来源创建 `crawl_run`。
2. Adapter 拉取列表页并产出候选 URL。
3. 通过规范化 URL 和内容指纹去重。
4. 对新增或发生变化的页面抓取详情并保存原文。
5. 发现附件后下载到本地对象目录，并记录 SHA-256。
6. 单条失败不终止整个来源；达到阈值后将来源运行标记为失败。

Adapter 最小接口：

```python
class SourceAdapter(Protocol):
    async def discover(self, cursor: dict | None) -> list[DiscoveredItem]: ...
    async def fetch_detail(self, item: DiscoveredItem) -> RawDocumentInput: ...
```

存储、去重、重试和日志由公共流水线完成，不放入各来源 Adapter。

JAI-011 起增加仓库内可手工维护的 `config/source_catalog.toml`，作为候选网站、地区、接入状态和来源级标题关键词的版本化清单。该清单不替代 `sources` 运行表：只有 `implementation_status = "active"` 且 `enabled = true`、并已有显式注册 Adapter 的条目才能进入采集；待验证的动态门户保持 `planned`/停用。分类覆盖校招、公职考试、央国企和外企官方招聘；非官方商业平台不进入可执行网站库，其人工参考和授权边界见 [`docs/REFERENCE_SOURCES.md`](REFERENCE_SOURCES.md)。目标名单和维护方法见 [`docs/SOURCE_CATALOG.md`](SOURCE_CATALOG.md)。

### 6.2 解析与抽取

解析优先级：确定性规则 > 表格映射 > LLM 补充。

1. HTML 清理导航、脚注和重复文本。
2. PDF 按页提取文本；文本密度过低则标记 `ocr_required`，V1 不强制 OCR。
3. Excel 识别工作表、标题行和合并单元格，保留原始行号/单元格证据。
4. 规则先抽取时间、链接、单位和地区。
5. 对不规则正文调用 LLM，要求严格 JSON Schema 输出。
6. 校验日期逻辑、枚举、必填字段和证据；异常进入人工复核队列。

### 6.3 匹配排序

V1 使用可解释规则，不依赖 LLM 直接打总分：

```text
总分 = 硬条件通过 × (
  地区匹配 25 +
  岗位关键词/方向 30 +
  专业匹配 15 +
  单位类型偏好 10 +
  截止紧迫度 10 +
  信息完整度 10
)
```

- 学历不满足、明确排除词命中、已截止属于硬过滤。
- 每个分项记录规则、输入和得分，支持解释与重算。
- 第 10 周以后再评估 embedding 召回或 LLM rerank，不能替代硬条件。

### 6.4 日报与推送

日报固定为四组：

1. **优先投递**：高匹配且报名窗口开放。
2. **即将截止**：未来 72 小时内截止。
3. **今日新增**：当天首次发现且未进入前两组。
4. **需要确认**：缺少截止日期、岗位表解析失败或关键字段冲突。

每条包含标题、单位、地区、截止日期、推荐理由、风险/缺失项、报名入口和原文链接。推送需幂等，同一日报同一通道默认只成功发送一次。

## 7. 十周交付计划

### 第 1 周：工程基线与纵向技术验证

**目标**：项目可启动，并用一个真实样本打通“网页 → 原文 → PDF 文本”。

- 初始化项目结构、依赖、配置和日志。
- 建立 Docker Compose：API + PostgreSQL。
- 提供 `/health/live`、`/health/ready`。
- 建立测试框架和 CI 基线。
- 选择首个静态来源，完成 HTML/PDF 技术验证。

**周验收**：新环境按 README 可启动；数据库迁移可执行；真实公告及其 PDF 可被保存和提取文本。

### 第 2 周：数据模型与采集框架

**目标**：公共采集流水线稳定，来源逻辑可插拔。

- 实现核心表、约束、索引和首版迁移。
- 实现 Adapter 协议、HTTP 客户端、限速、重试和超时。
- 实现 URL 规范化、内容指纹和幂等写入。
- 实现附件发现、下载、校验和存储。
- 建立可手工维护的网站库和来源级包含/排除关键词。
- 接入来源 1（优先国务院国资委公开招聘栏目）。

**周验收**：相同任务连续运行两次不产生重复记录；单条失败有日志且不会中断整批任务。

### 第 3 周：首批来源与运行记录

**目标**：覆盖至少三种页面结构，建立可观测采集能力。

- 接入来源 2、3。
- 实现 `crawl_runs` 统计、错误分类和失败重跑。
- 增加手动运行命令/API。
- 为三个来源建立 HTML 固定样本回归测试。
- 从网站库中按“官方公开、无需登录、结构稳定、信息价值”顺序选择来源 2、3；报名系统和未验证动态门户不得直接启用。

**周验收**：三个来源均可增量运行；能查看发现、新增、更新、跳过和失败数量。

### 第 4 周：PDF/Excel 附件解析

**目标**：附件转为可追溯的标准中间数据。

- PDF 页级文本提取、加密/扫描识别和错误状态。
- XLSX/XLS 工作表、表头和合并单元格处理。
- 建立解析器注册表和统一输出协议。
- 建立至少 10 份真实脱敏附件的黄金样本集。

**周验收**：支持的附件批量解析成功率达到 80%；输出能定位到页码、行号或单元格。

### 第 5 周：公告与岗位结构化抽取

**目标**：从正文和附件生成 `job_posts`、`job_positions`。

- 实现日期、地区、单位、报名链接等规则抽取。
- 实现 LLM provider 抽象、JSON Schema、超时和重试。
- 合并正文与附件结果，处理字段冲突。
- 保存字段证据、置信度和抽取版本。
- 建立结构化抽取回归测试。

**周验收**：黄金样本核心字段完整率达到 85%；错误日期不会静默入库。

### 第 6 周：质量控制与五来源覆盖

**目标**：达到 MVP 来源数量，并让异常可发现、可恢复。

- 接入来源 4、5：优先国家大学生就业服务平台和上海市人社局事业单位公开招聘；若动态入口不满足公开访问边界，使用同一官方主体的稳定公告入口或记录阻塞。
- 实现字段校验、人工复核状态和重新解析。
- 增加来源健康状态、连续失败告警数据。
- 完成数据回填与重复数据检查。

**周验收**：5 个来源连续运行 3 天；所有失败均有明确分类和可重试路径。

### 第 7 周：偏好、评分与日报

**目标**：从数据管道转化为个人可用的信息产品。

- 实现单用户偏好配置。
- 实现硬过滤、分项评分、版本化和解释。
- 实现日报查询、分组、Markdown/HTML 模板。
- 使用历史样本人工检查 Top 20 排序。

**周验收**：日报中每条推荐都有得分解释和原文链接；修改偏好后可全量重算。

### 第 8 周：调度、微信推送与 MVP 发布

**目标**：系统每天无人值守完成闭环。

- 实现每日调度、并发锁和错过任务处理。
- 接入一个微信推送通道。
- 实现推送幂等、重试和失败记录。
- 完成端到端测试、备份恢复说明和运行手册。
- 建立 `v0.1.0-mvp` 发布清单。

**周验收**：连续 5 次自动运行完成“采集 → 解析 → 匹配 → 日报 → 推送”，且无重复推送。

### 第 9 周：最小配置控制台与查询 API

**目标**：降低日常维护成本，为 Agent 暴露稳定工具层。

- 提供来源列表/启停、偏好编辑、运行历史和失败详情 API。
- 实现最小配置页面；不建设通用管理后台。
- 实现岗位搜索、岗位详情、评分解释服务。
- 为工具层补充权限边界和审计日志。

**周验收**：无需改数据库或配置文件即可完成日常设置和故障定位。

### 第 10 周：Agent 接入与稳定性收尾

**目标**：以自然语言查询和受控操作现有系统。

- 实现 `search_jobs`、`get_job_detail`、`explain_match`、`generate_report`、`run_crawl` 工具。
- 建立 Agent 指令、工具参数 Schema、确认策略和最大步数。
- 对查询、解释、重新生成日报和手动采集做评测。
- 修复稳定性问题并发布 `v0.2.0-agent`。

**周验收**：预设任务集成功率 ≥ 90%；写操作有审计记录，重复请求保持幂等。

## 8. 测试策略

### 8.1 测试金字塔

- **单元测试**：URL 规范化、日期解析、表头识别、评分规则、模板渲染。
- **契约测试**：每个 Adapter 对固定 HTML 样本输出一致结构。
- **集成测试**：数据库、附件存储、LLM mock、推送 mock。
- **端到端测试**：从固定来源样本到日报生成，CI 中不依赖真实外网。
- **线上冒烟**：只检查少量页面与选择器，不在 CI 高频访问目标网站。

### 8.2 黄金样本

- 每接入一个来源至少保留 3 个列表页、3 个详情页样本。
- PDF/Excel 共至少 10 份，覆盖多页表格、合并单元格、空行和不同日期格式。
- 样本若含个人信息必须脱敏；确认许可后再提交仓库。
- 解析规则或 Prompt 修改后必须跑完整回归集。

## 9. 安全、合规与成本

- 遵守目标网站服务条款、robots 规则和合理访问频率；不绕过登录、验证码和访问控制。
- User-Agent 标识应用，设置来源级限速、超时和指数退避。
- Token、数据库密码和推送密钥仅放环境变量；`.env` 不提交仓库。
- 日志不记录密钥、完整简历或不必要的个人信息。
- LLM 请求默认只发送完成抽取所需的公告片段；记录 token 与调用成本。
- 设置每日 LLM 调用预算和熔断阈值，失败后进入待处理队列而非无限重试。

## 10. 风险与应对

| 风险 | 概率/影响 | 应对与退出条件 |
|---|---|---|
| 网站结构频繁变化 | 高/高 | Adapter 契约测试、选择器健康检查；连续失败后自动停用并告警 |
| 动态站/验证码阻塞 | 中/高 | V1 优先公开静态源；若 1 天内无法稳定获取则替换来源 |
| 附件格式复杂 | 高/高 | 保留原文件与证据；不支持的扫描件进入人工队列，不阻塞公告入库 |
| LLM 抽取幻觉 | 中/高 | Schema、证据、确定性校验；关键日期无证据则标记缺失 |
| 个人开发范围膨胀 | 高/高 | 每周只完成 P0；P1 可延期，P2 不进入当前 Sprint |
| 推送通道不稳定 | 中/中 | 幂等、重试、日报持久化；可在页面直接查看日报 |
| 维护成本超过收益 | 中/高 | 以每日维护 ≤10 分钟为门槛，移除不稳定低价值来源 |

## 11. 项目管理约定

### 11.1 里程碑

| Milestone | 周期 | 完成标志 |
|---|---|---|
| M1 Foundation | W1 | 工程可启动，纵向技术验证完成 |
| M2 Collection | W2–W3 | 3 个来源稳定增量采集 |
| M3 Extraction | W4–W6 | 5 个来源完成解析、抽取和质量控制 |
| M4 Intelligence | W7 | 匹配和日报可用 |
| M5 MVP Release | W8 | 自动调度和推送闭环上线 |
| M6 Agent | W9–W10 | 配置控制台与 Agent 工具上线 |

### 11.2 优先级

- `priority:P0`：阻塞当前里程碑或 MVP 核心闭环。
- `priority:P1`：显著改善可靠性或维护效率，可在周内有余量时完成。
- `priority:P2`：增强项，默认进入 MVP 后 backlog。

### 11.3 Definition of Ready

Issue 开始前必须具备：目标、范围、验收标准、依赖、测试方式和非目标。数据源 Issue 还需记录入口 URL、页面类型、预期访问频率和合规检查。

### 11.4 Definition of Done

- 实现与验收标准一致，无隐藏范围。
- 关键逻辑有自动化测试，全部检查通过。
- 数据库变更包含可执行迁移。
- 配置项进入 `.env.example`，无密钥入库。
- 日志和错误信息足以定位失败来源与步骤。
- 用户可见或运维行为已更新 README/运行手册。
- 对应 Issue 记录验证证据后关闭。

## 12. 阶段闸门与调整规则

- **W2 闸门**：若首个来源无法幂等采集，不增加新来源，先修公共流水线。
- **W4 闸门**：若附件解析成功率低于 60%，将扫描/OCR 明确移出 MVP，并更换高价值样本验证。
- **W6 闸门**：若 5 个来源导致维护负担过高，允许以 3 个稳定来源进入 MVP，稳定性优先于数量。
- **来源扩展闸门**：11 个官方候选站和外企专区不阻塞首个 MVP；任何站点需要登录、验证码、规避反爬或违反条款时保持停用，并把原因写入网站库和 WORKLOG。
- **W8 闸门**：只有无人值守连续运行 5 次后才标记 MVP 完成。
- **Agent 闸门**：MVP 数据闭环未稳定时，第 9–10 周继续修数据管道，不提前接入 Agent。
